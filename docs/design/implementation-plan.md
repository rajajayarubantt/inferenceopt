## 0. Decisions Recorded

| Topic | Decision | Notes |
|---|---|---|
| License | **Apache-2.0** | Explicit patent grant and patent-retaliation clause. Matches vLLM and TensorRT-LLM, and is compatible with MIT dependencies (LiteLLM, llama.cpp). |
| UI stack | **React + Vite + TypeScript** in top-level `ui/`, served by **FastAPI** | Built assets ship inside the wheel. End users never need Node.js. |
| Distribution | **PyPI** (`pip install inferenceopt`), pure-Python wheel (`py3-none-any`) | The UI is static files, so no platform-specific wheels are needed. |
| Runtime adapters | Build **all** (llama.cpp, vLLM, TensorRT-LLM). **Test only llama.cpp for now.** | vLLM and TensorRT-LLM ship marked `experimental / untested on hardware` until you validate them. |
| Package name | **`inferenceopt`** | `pip install inferenceopt`, `import inferenceopt`, `inferenceopt ui`. Optional short CLI alias `iopt`. |

### Changes to Plan.md this introduces

1. **The API is no longer "optional, later".** The UI controls everything, so the FastAPI server is a core component from Phase 1.
2. **A new `services/` layer.** The CLI, the REST API and the Python API are all thin wrappers over the same service functions. This guarantees that anything the CLI can do, the UI can do too.
3. **Runtimes are external processes, not pip dependencies.** Each adapter launches the runtime (`llama-server`, `vllm serve`, `trtllm-serve`) as a separate process or container and talks to it over its OpenAI-compatible HTTP endpoint. This keeps `pip install inferenceopt` small, avoids torch/CUDA dependency conflicts, and matches the isolation model in Plan.md §11.
4. **Local web-server security moves to Phase 1.** A UI that can start processes on the host needs auth from day one.

## 2. Packaging and Publishing Design

### 2.1 `pyproject.toml` essentials

```toml
[build-system]
requires = ["hatchling", "hatch-vcs"]
build-backend = "hatchling.build"

[project]
name = "inferenceopt"
dynamic = ["version"]
requires-python = ">=3.11"
license = "Apache-2.0"                      # PEP 639 SPDX expression
license-files = ["LICENSE", "NOTICE"]        # JS third-party notices ship inside _ui/
dependencies = [
  "typer", "rich", "pydantic>=2", "pydantic-settings", "pyyaml",
  "fastapi", "uvicorn[standard]", "httpx", "sqlalchemy>=2", "alembic",
  "jinja2", "psutil", "nvidia-ml-py", "platformdirs",
]

[project.optional-dependencies]
llm      = ["litellm"]                       # planner (pinned exactly in uv.lock)
optimize = ["optuna"]                        # Bayesian search
quality  = ["lm-eval"]                       # optional lm-evaluation-harness
all      = ["inferenceopt[llm,optimize,quality]"]

[project.scripts]
inferenceopt = "inferenceopt.cli:app"

[project.entry-points."inferenceopt.runtimes"]      # third-party adapters can plug in
llamacpp     = "inferenceopt.runtimes.llamacpp:LlamaCppAdapter"
vllm         = "inferenceopt.runtimes.vllm:VLLMAdapter"
tensorrt_llm = "inferenceopt.runtimes.tensorrt_llm:TRTLLMAdapter"

[tool.hatch.version]
source = "vcs"                               # version comes from the git tag

[tool.hatch.build.targets.wheel]
artifacts = ["src/inferenceopt/_ui/**"]             # include gitignored built UI

[tool.hatch.build.targets.sdist]
artifacts = ["src/inferenceopt/_ui/**"]             # building from sdist doesn't need Node
```

- **No `vllm` or `tensorrt-llm` extras.** Those runtimes bring torch and CUDA pins that would conflict with each other and with the user's environment. Adapters find them by executable path, by a Python environment path, or by a Docker image. The UI has a "configure runtime" form for this.
- **Base install includes the UI server.** `pip install inferenceopt && inferenceopt ui` must work with nothing else installed.

### 2.2 Release pipeline (`release.yml`)

1. Push tag `vX.Y.Z`.
2. `pnpm install --frozen-lockfile && pnpm build` writes `src/inferenceopt/_ui/`, plus a generated `THIRD_PARTY_LICENSES.txt` for the bundled JS.
3. `uv build` produces the sdist and wheel.
4. Verify the wheel: check that `_ui/index.html` is present, run `twine check`, then install the wheel into clean venvs on Linux, Windows and macOS, run `inferenceopt doctor`, start `inferenceopt ui`, and `GET /`.
5. Publish to **TestPyPI**.
6. After **manual approval** (a GitHub Environment `pypi` with required reviewers), publish to **PyPI** via **Trusted Publishing** (OIDC, no API tokens stored). This also produces PEP 740 attestations.
7. Create a GitHub Release with notes taken from CHANGELOG.

### 2.3 Versioning

- SemVer. Stay on `0.x` until the schemas and the Python API are stable. `1.0.0` is reached at Milestone D.
- Data schemas (job YAML, manifest, DB) carry their own `schema_version`, with migrations.

## 3. UI Design

### 3.1 Architecture

```text
Browser (React SPA) ──REST──▶ FastAPI routes ──▶ services/ ──▶ core modules
        ▲                                  │
        └────────SSE (events)──────────────┘
                                           │
                       experiments/ worker process(es) ─▶ runtime processes
```

- **Jobs never run inside request handlers.** The server hands each job to a worker process. Job state lives in SQLite, so a job survives the browser closing, and the CLI and UI can watch the same job.
- **REST for commands, SSE for live streams** (trial progress, metrics, logs). SSE is simpler than WebSockets and sufficient here.
- **Typed contract.** `scripts/gen_api_client.py` exports the OpenAPI schema and generates `ui/src/api/` with `openapi-typescript`. CI fails if the generated client is stale.
- **Frontend libraries:** React, TanStack Router, TanStack Query, Tailwind and shadcn/ui, ECharts (for Pareto scatter plots and latency distributions), react-hook-form + zod (job wizard).

### 3.2 Pages

| Page | Purpose |
|---|---|
| Dashboard | System status, running jobs, recent results, doctor warnings |
| Hardware | Scan, devices, memory, capability badges (detected / inferred / user-specified) |
| Models | Browse registry, inspect, add a local GGUF or HF reference, license and provenance |
| Runtimes | Detected runtimes and versions, support level (tested / experimental), binary/env/image config, optional "install llama.cpp" with consent and checksum |
| New Job wizard | Model → workload → objective → constraints → budget → **plan preview → Approve** |
| Job detail | Live trial stream, logs, cancel, rejection reasons, Pareto chart, compare trials |
| Planner (LLM) | Provider/model alias, test connection, privacy toggles, budget, audit log of every call |
| Deploy | Generate a bundle from a trial, preview files, download zip, tested vs. untested labels |
| Reports | Export Markdown, JSON or CSV |
| Settings | Paths, storage, retention, server/auth, local-only mode |

### 3.3 Local server security (Phase 1, not deferred)

- Binds to `127.0.0.1` by default. Binding to `0.0.0.0` requires `--allow-remote` and keeps token auth on.
- A random session token is printed in the launch URL (the same pattern as Jupyter) and moved into an HttpOnly cookie on first load.
- Host-header allowlist (prevents DNS rebinding) and Origin checks. No CORS by default.
- **Secrets are write-only.** The API never returns API keys; the UI shows only "set / not set".
- No endpoint executes arbitrary commands. Runtime launches go through adapter allowlists only.
- Every action that downloads, uploads, starts a long job or deploys requires an explicit confirmation step, enforced on the server, not only in the UI.

### Phase 2: Hardware and model inventory

**Backend**
- CPU, RAM, OS and Python detection (`psutil`, `platform`, CPU flags via `/proc/cpuinfo`, `sysctl` or `cpuid`).
- NVIDIA detection through NVML (`nvidia-ml-py`) that degrades gracefully when NVML is absent. AMD and Apple are plugin stubs only.
- Every property tagged `detected | inferred | user_specified`. Free and total memory reported separately.
- Model registry: a curated YAML registry plus "add local model" support (reads GGUF metadata headers and HF `config.json` without downloading weights). License and provenance fields.
- Memory estimator (weights + KV cache + overhead + safety margin), with an uncertainty range, always labelled as an estimate.
- Compatibility queries (model × runtime × hardware) and a preflight report.
- CLI: `hardware scan`, `models list|inspect|add`, `preflight`.
- API: `/hardware`, `/models`, `/preflight`.

**UI:** Hardware page, Models page (list, inspect, add local model), and a preflight panel ("Will this fit?") with the estimate range and its assumptions.

**Tests:** property tests for the estimator (monotonic in context length, batch size and dtype size); golden tests for GGUF metadata parsing.

**Exit criteria:** A correct inventory on your Windows machine and in CI, impossible configurations rejected before any trial, and every estimate labelled as one.

### Phase 3: Runtime adapters (all built, llama.cpp tested)

**Backend**
- `RuntimeAdapter` interface: `detect()`, `capabilities()`, `validate(config)`, `build_launch(config) -> LaunchSpec`, `start()`, `health()`, `stop()`, `export_config()`, and `support_level`.
- `LaunchSpec` is a structured object (executable, argv list, env, ports, mounts), **never a shell string**.
- Shared async OpenAI-compatible client for streaming completions, used by every adapter for benchmarking.
- **llama.cpp adapter (tested):** drives the `llama-server` binary rather than `llama-cpp-python`, which lags upstream. Supports a user-supplied binary path, auto-detection, and an optional consented download of an official release with checksum verification. Capabilities parsed from `--help` or version output.
- **vLLM adapter (experimental):** `vllm serve` via a configured environment path or Docker image. Linux/WSL2 only; reports "unsupported on native Windows" on Windows.
- **TensorRT-LLM adapter (experimental):** `trtllm-serve` via Docker image. Engine-build step modelled as a separate, cancellable stage.
- Process supervision: port allocation, startup timeout, log capture, OOM and crash detection, guaranteed cleanup (including Windows job objects so child processes die with the parent).
- CLI: `runtimes list|inspect|configure`, `serve --dry-run` (shows the exact launch spec).

**UI:** Runtimes page with tested/experimental badges, configuration forms, a "dry-run launch" preview, and start/stop of a smoke-test server.

**Tests**
- **llama.cpp:** a real integration test in public CI (CPU, tiny GGUF): start, health check, generate, stop, plus a forced-OOM or bad-config failure path.
- **vLLM and TensorRT-LLM:** contract tests only, meaning golden snapshots of the generated `LaunchSpec`, capability parsing against recorded `--help` fixtures, and a run against a **fake OpenAI-compatible server**. Hardware tests are written now but marked `@pytest.mark.hardware_vllm` / `hardware_trtllm` and skipped, ready for your later validation.

**Exit criteria:** The same workload runs through the adapter interface on llama.cpp, failures are recorded correctly, and the experimental adapters pass contract tests and are clearly labelled in the CLI, UI and docs.

### Phase 4: Benchmark harness, quality gates and job runner

**Backend**
- Workload traces (versioned, seeded), cold vs. warm modes, warm-up, repetitions and concurrency profiles.
- Metrics: load time, TTFT, ITL, end-to-end latency (p50/p95/p99 with a sample-size guard), prefill and decode tokens/s, **per-request vs. aggregate** throughput, error rate, peak VRAM and RAM (sampled by a sidecar monitor).
- Raw samples are stored alongside summaries, and reports can be regenerated from the raw data.
- Quality: exact-match, JSON-schema validity, and a small versioned task set. The regression threshold acts as a **gate**. Optional `lm-eval` integration behind an extra.
- `experiments/`: job scheduler, worker process, trial state machine (`pending → preflight → starting → warming → measuring → evaluating → accepted|rejected|failed`), cancellation and crash recovery on restart.
- CLI: `bench run`, `trials list`, `results show`, `report export`.
- API: `/jobs`, `/jobs/{id}/events` (SSE), `/trials`, `/reports`.

**UI:** a "Run baseline benchmark" flow, a live job page (stage timeline, streaming metrics, logs, cancel button), trial detail, and report export.

**Exit criteria:** Repeated llama.cpp runs are comparable within a declared tolerance, a quality failure blocks acceptance, and closing the browser does not kill the job.

**→ Release `0.1.0` to PyPI (Milestone A minus search):** scan, preflight and baseline benchmark via CLI and UI.

### Phase 5: Deterministic optimizer

**Backend**
- Candidate space generated from adapter capabilities, with allowlist and bounds enforcement.
- Stage A feasibility filter, Stage B baseline and one-at-a-time sensitivity, Stage C grid/random search (Optuna Bayesian search behind the `optimize` extra).
- Documented early-stopping rules, Pareto frontier computation, re-runs of top-k candidates for variance, and storage of every rejection reason.
- CLI: `optimize --job job.yaml`.

**UI**
- **New Job wizard** with a plan preview (candidate count, estimated time and disk use) and an explicit **Approve** step.
- Job detail adds a trials table (sortable, with reasons), an interactive Pareto chart, side-by-side trial comparison, and a "why rejected" panel.

**Exit criteria:** On llama.cpp CPU, the optimizer matches or beats the default on at least one declared workload without violating constraints, and failed trials never corrupt a job.

**→ Release `0.2.0` (Milestone A complete).**

### Phase 6: LiteLLM planner

**Backend**
- `llm/`: LiteLLM gateway with model aliases, `api_base`, timeouts, retries, and a per-job call and cost budget. **Local-only mode** means no external calls, with a test that asserts this.
- A privacy filter builds the minimal payload according to the `send_*` flags, and all LLM output is treated as untrusted.
- `planner/`: strict structured-output schema, validation against adapter capabilities, deduplication against previous trials, fallback to deterministic search, and a `PlannerCall` audit record (provider, model, prompt template version, response hash, usage).
- Ablation switch: the same job can run with or without the planner for comparison (Plan.md H3).
- CLI: `llm test`, `llm audit`.

**UI:** a Planner settings page (secret fields are write-only), a "test connection" button, privacy toggles with a "this is exactly what will be sent" preview, an audit log, and the planner's hypotheses shown inline on trials ("proposed by planner", hypothesis text, measured outcome).

**Tests:** a mock LiteLLM provider, invalid or malicious proposals rejected, a provider outage that does not stall the job, and no secrets in logs or the database.

**Exit criteria:** Plan.md Phase 6 exit criteria, all reachable from the UI.

**→ Release `0.3.0`.**

### Phase 7: Deployment bundle generation

**Backend**
- Jinja2 templates: `runtime-config.yaml`, `start.sh` **and** `start.ps1`, `healthcheck`, `Dockerfile` and `compose.yaml` (when supported), `manifest.json` (hashes, versions, exact benchmark command), `benchmark-report.{json,md}`, `environment.lock`, and `rollback.md`.

**UI:** a Deploy page that previews each generated file, shows tested/untested property labels, downloads a zip, and offers a "Reproduce on this machine" button.

**Exit criteria:** A generated llama.cpp bundle reproduces on a second machine (or a clean venv) within the declared tolerance.

**→ Release `0.4.0` (Milestone B).**

### Phase 8: Safety and production hardening

**Backend**
- Container-isolated workers where Docker is available (non-root, CPU/memory/pids limits, read-only mounts, `--network none` after artifacts are present).
- **Fallback for Windows and hosts without Docker:** process-level limits (job objects or rlimits) with a visible **"reduced isolation"** label. High-risk candidates (generated code, kernels) are refused in this mode.
- Archive extraction protection (path traversal, symlinks, size bombs), and download/network policy enforcement.
- SBOM (CycloneDX) for Python and JS, `pip-audit` and `pnpm audit` in CI, CodeQL.
- Retention policies for logs and traces, concurrent-job tests, and DB recovery tests.
- Optional remote mode hardening: TLS guidance, a stronger auth option, rate limiting.

**UI:** an isolation-level indicator on every job, a retention settings page, and a security status section on the Dashboard.

**Exit criteria:** Plan.md Phase 8 exit criteria, plus a documented threat model in `docs/safety.md`.

**→ Release `1.0.0` (Milestone D)** after your own vLLM/TRT-LLM validation, or ship 1.0 with them still labelled experimental.

## 5. Cross-cutting Practices

- **Feature parity rule:** a PR that adds a service function must add its CLI command, API route and UI surface, or open a tracked issue for the missing ones.
- **Test markers:** `unit`, `property`, `integration_llamacpp`, `contract`, `server`, `e2e`, `hardware_nvidia`, `hardware_vllm`, `hardware_trtllm`. Public CI runs everything except `hardware_*`.
- **Docs per feature:** each phase ends with updated `docs/` and a screenshot-based UI guide section.
- **Changelog:** every PR updates `CHANGELOG.md` under `Unreleased`.
- **Contributions:** DCO sign-off (`git commit -s`), no CLA. This is the standard lightweight choice for Apache-2.0 projects.
